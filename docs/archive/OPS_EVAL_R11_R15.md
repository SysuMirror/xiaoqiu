# 小秋 Ops 使用者评估报告（第 11-15 轮 · R11-R15）

> 评估基准：R11-R15 五轮的真实生产数据；对照 R6-R10 阶段评估的五条建议逐条核销。

## 一、迭代效果

**R11 存储容量治理**：1h 降精度层上线（90 天保留，RRD/Thanos 近细远粗模式），流量窗口从 3 档扩到 5 档（30m/6h/24h/**7 天/30 天**）；error_samples 保留 3→7 天（R5 首份建议核销）；ops_notifications 90 天清理自动执行；/ops/storage 容量总览可查（实测日增约 1.6MB，90 天不到 150MB——**存储增长完全可预测**）。R10 阶段评估建议 1 已核销。

**R12 开放标准互操作**：/metrics 从"能看"升级到"可被标准采集器消费"——HELP 注册表 18 条 + TYPE 声明补全 + 无样本指标也输出 schema（采集端稳定不闪断）。docs/GRAFANA_INTEGRATION.md 提供双源采集配置（含 Go Bearer 认证）、10 条核心 PromQL 速查、最小面板 JSON——**Grafana 一页接入零改代码**。R10 建议部分核销。

**R13 LLM 归因升级**：从"模块级标注"进化到"根因假设+工具验证闭环"——事实包（模块卡+24h 指纹+30m RED+30 天误报反馈四源）→ LLM 生成 2-4 假设 → 逐假设调确定性工具验证（search_routes/triage 真跑）→ 高/中/低三档置信度 → 写回图上标注。误报反馈回路（面板 ✓✗ → 台账 → 后续归因 prompt 降权）让归因越用越准。验收实测 2/2 假设 verified + 高置信。

**R14 审计与账号安全**：actions 台账消费面补齐——/ops/audit 查询 API + 面板审计 tab（类型 chip 筛选/时间线/result 颜色分级）+ 登录暴力尝试检测（login_failures_1h 指标 + critical 告警规则——R6 框架即插即用）。R10 阶段评估建议 4（登录审计联动）核销。

**R15 SLO 与错误预算**：SLO 定义落 PG（面板可配，seed 全局 99% + 核心路径 99.5%）；错误预算计算复用 R11 的 1h 表（30 天窗口）：预算=(1-target)×总量、剩余、燃尽率（burn rate）；燃尽率>2x 触发 warn 告警（Google SRE burn rate 模式）；流量台账顶部 SLO 状态条（可用性百分比+预算剩余+⚠️标记）。**R15 同时是纲领第二份评估报告的节点轮**。

## 二、现存问题

1. **SLO 样本积累不足**：1h 表 R11 才上线（<24h 数据），30 天窗口的 SLO 读数目前只反映近期——需要 30 天后读数才稳定。
2. **refresh 500 仍未修**（Go 侧，三轮报告连续点名）：观测证据链完整（指纹/样本/request_id/trace/LLM 归因可跑），属主站代码修复，观测面无法代修。
3. **psutil 生产未装**（R10 遗留）：agent 容器内存/线程指标仍降级 None——需镜像重建。
4. **burn rate 单窗口**：当前只算 30 天窗口的燃尽率，Google SRE 推荐多窗口（1h/6h/3d）交叉判定——快速燃尽检测有盲区（当前流量下风险低）。
5. **归因 LLM 成本**：每次归因= 1 次假设生成 + 最多 4 次工具验证调 ReAct Agent（单次）——成本可控但流量上来后需频控加严。

## 三、使用痛点

1. **SLO 条与流量图分离**：SLO 状态在流量台账顶部，点开流量才能看——单看 SLO 状态需两次点击（可考虑加到 header chip）。
2. **审计 tab 无时间轴可视化**：列表形式足够但缺乏"什么时候动作密集"的直观图（R5 图表基座可复用，但优先级低于功能）。
3. **LLM 归因 10-30s 等待**：异步体验可接受但无进度指示（与 R10 报告的 L2 诊断痛点同源）。
4. **30 天流量图桶数多**：43200 分钟窗口 = 720 个 1h 桶，ECharts 渲染无压力但 tooltip 信息密度低。

## 四、优化建议（R16-R20 排期建议）

1. **R16 故障自愈剧本库**（已排期）：把 LLM 归因的高置信假设与 L3 动作链衔接——"归因→建议动作→人确认执行"完整闭环；常见故障（磁盘/内存/容器重启）预置剧本。
2. **R17 攻击面收敛**（已排期）：CSP 去 unsafe-inline（R8 外链 JS 化的顺路收益）、token 轮换脚本化、/ops/auth 登录端点 IP 白名单可配。
3. **R18 水平扩展前兆**（已排期）：R9 记录的多 worker 前置条件（APScheduler 分布式/errtail 单写者）在这一轮解；agent 无状态化收尾。
4. **R19 容灾与备份体系**（已排期）：备份推 COS（异地——R10 指出的同盘风险）、配置版本化（git 管服务器配置）、降级预案文档化。
5. **R20 第二次生产化 + 终局**（已排期）：psutil 入镜像、refresh 500 联合修复（Go 侧）、全量回归 + 恢复演练第二轮 + 长期运维方案（值班/巡检/容量规划文档）。

**总体结论**：R11-R15 五轮完成了从"功能堆叠"到"运营度量"的跨越——存储增长可预测（1.6MB/天）、指标可被外部标准消费（Grafana 一页接入）、根因分析有闭环（假设→验证→反馈→降权）、操作全留痕（审计 tab）、服务质量有度量（SLO+错误预算+燃尽率）。R1-R15 的十五轮已覆盖十个维度中的七个完全体 + 三个半成品（自动化运维 R7 L3 仅容器重启、安全加固 R10 仅响应头、弹性扩容 R11 仅存储面）——R16-R20 五轮聚焦补全这三个半成品并完成第二次生产化收口。"全站运维 100% 依赖小秋 Ops"的差距收敛至：故障自愈（R16）、攻击面彻底收敛（R17）、水平扩展（R18）、异地容灾（R19）四步。
