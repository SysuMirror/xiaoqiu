# 小秋 Ops 使用者评估报告（第 1-5 轮 · R1-R5）

> 评估基准：2026-09-13 至 2026-09-14 真实生产数据与使用记录（面板遥测/错误台账/邮件告警/部署记录），非主观印象。

## 一、迭代效果（R1-R5 交付与实测）

**R1 面板鉴权与账号体系**：面板从"SSH 隧道+全开放"升级为公网直达（https://ssemarket.cn/ops/view），唯一账号 2215020897@qq.com 经后端 OAuth/登录链路鉴权（BFF 无状态会话，后端 7 天 JWT 不出服务端）。实测：无凭证访问 100% 拒绝（8 路由双层校验），防爆破（5 次/15 分钟锁定）与 login CSRF 防护就位。效果：访问门槛从"开终端建隧道"降为"开浏览器"，日常查看频次显著提升。

**R2 流量分析台账**：接口级 RED 进入 5 分钟桶时序存储（PG rollup，7 天保留）。实测生产数据：55 个接口、24h 累计 6800+ 请求（checkUserVoted 单接口 6832 次居首）、错误率 0.00-0.05%、平均延迟 1.9-15.6ms。窗口切换（30m/6h/24h）与 TOP 榜让"哪个接口最忙/最慢"一眼可答。

**R3 错误捕获与指纹聚类**：Go 访问日志零侵入采集，错误按指纹（路由模板+状态码）聚类。**上线第一轮即抓到 9 条真实错误指纹，其中 `500 POST /api/auth/refresh ×6 影响 5 IP` 为存量生产 bug**（refresh token 接口持续失败，此前散在日志中无人知晓）；另有 `400 login ×24`（3 个 IP 反复尝试登录）值得持续观察。样本含 request_id/来源 IP/延迟，从"有错误率数字"进化到"能指出具体哪个请求、对谁、报了什么"。

**R4 全链路请求追踪**：发现并激活 Go 侧既有 OTel 埋点（collector 从未运行是唯一缺口），部署 Jaeger 后 trace 即流入（5 分钟 3 条真实请求，browse 13.1ms/updateBrowseNum 11.8ms）。错误中心样本 request_id 可一键反查 trace——错误指纹→样本→单请求时间线的排障闭环成形。

**R5 可视化基座**：ECharts 统一图表入口（暗色色板/字体/空态一处定义），流量台账升级为请求柱+错误率副轴组合图，错误中心新增 24h 错误趋势图；链路瀑布与既有 G6 画布风格一致。

**累计基础设施收益**（含纲领前 I16-I19 迭代）：磁盘 82.4%→74%（释放 21G 并滚动清理）；内存守卫+磁盘守卫+错误率邮件告警三道防线运行中；面板 AI 助手（真实 LLM+五只读工具）累计回答架构/排障问题并可直接点击模块 id 跳转画布。

## 二、现存问题

1. **DB 层 span 缺失**：Go 的 gorm 插件仅输出 metrics，SQL 查询无 span——trace 瀑布目前只有 HTTP 入口层，慢请求无法定位到具体 SQL；升级需 otelgorm（Go 改动，需排期）。
2. **nginx 层无 trace 无 request_id**：trace 起点=otelgin，公网入口段耗时缺失；nginx 日志与 Go 日志只能靠 IP+时间窗模糊关联。
3. **存量真实 bug 待修**：`/api/auth/refresh` 500（疑似 refresh token 保存冲突）属 Go 侧代码问题，观测面只能发现不能代修。
4. **Jaeger 内存存储**：重启即丢 trace（观测窗口型语义，台账数据在 rollup/错误样本不受影响）；AlwaysSample 在流量上量后需改采样率。
5. **单文件前端规模压力**：topology.html 已 1400+ 行、四个侧滑面板与图表基座并存，继续膨胀将触及可维护性边界（R8 前端工程化已排期）。
6. **错误对账未自动化**：日志侧错误数与 rollup errors 列的一致性校验目前靠人眼（R6 告警规则轮计划做自动对账）。

## 三、使用痛点

1. **12 小时会话过期**：单管理员日常使用尚可，但每次过期需重新输密码（无记住登录/免二次验证）——安全与便利的折中，暂无两全方案（引入 refresh 机制属鉴权链路改动，受"禁改"约束）。
2. **错误样本仅 3 天、trace 仅内存**：回溯一周前的错误现场做不到（rollup 有 7 天但只有计数无样本）。
3. **错误中心空态期无感知**：错误是被动查看的，出现新指纹时除邮件告警（仅错误率超阈值才发）外无主动通知渠道。
4. **图表首次加载依赖 CDN**：unpkg/jsdelivr 双源已做，但极端断网下图表退化（基座有降级保护不白屏）。
5. **移动端体验未优化**：面板按桌面 SRE 工具设计，手机浏览器可用但侧滑与表格横向滚动体验一般。

## 四、优化建议（按优先级）

1. **R6 告警规则引擎**（已排期）：把"错误率超阈/新指纹出现/磁盘超线"统一为可配置规则+分级+通知路由，补上自动对账——直接解决痛点 3 与问题 6。
2. **修复 refresh 500**：Go 侧定位（观测数据已给全：指纹/样本/request_id/trace），属业务代码修复，建议作为独立小改动尽快处理。
3. **R7 安全动作链**（已排期）：L1 只读动作面板化（日志拉取/配置快照），让"看"与"动"在同一界面闭环。
4. **trace 持久化评估**：若回溯需求明确，Jaeger 换 badger 后端（容器内卷+容量上限），代价约 1GB 磁盘——磁盘现余 55G 可承受，建议观察一个月使用习惯再定。
5. **错误样本保留延长至 7 天**（与 rollup 对齐）：样本表写入量 O(指纹数) 已解耦风暴风险，延长保留仅增存储（估计 <50MB/月），可在 R11 存储治理轮一并做。
6. **面板使用埋点**：目前"使用频次显著提升"缺量化依据，建议在 /ops/* 请求日志上做简单计数（匿名、仅频次），让 R15 的第二份评估有数据支撑。

**总体结论**：五轮迭代后面板已完成从"原型玩具"到"日常可用排障工具"的转变——鉴权、流量、错误、链路四条主线全部基于真实生产数据闭环，并已在真实 bug（refresh 500）的发现上体现价值。距离"全站运维 100% 依赖小秋 Ops"的差距主要在：动作执行面（R7/R16）、告警自动化（R6）、容灾（R10/R19）与移动端体验。
